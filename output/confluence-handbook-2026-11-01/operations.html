Workspace development

  1. Clone the parent with recursive submodules, or initialize existing submodules before building.
  2. Inspect current package manifests and lockfiles; install dependencies per package with the required private-registry access.
  3. Use Node 24 for the reviewed workspace; check individual package engine constraints when changing runtime.
  4. Configure service-local environment files using each .env.example, with secrets held outside version control.
  5. Start the shared local database and required owning-service migrations, then run the selected application topology.
  6. Build shared UI dependencies and the host together; verify health and one authorized user journey.

Working-tree and release discipline

The reviewed workspace contains modified submodules and uncommitted local work. Capture reviewed source commits and compatible package versions before release. Do not assume local builds represent pinned parent revisions. Commit changes in the owning child repository and then update the parent pin.

Operational ownership

Each service owns its health, configuration, migrations, secrets and recovery procedure. The service catalog helps observe/discover endpoints; it cannot certify a financial transaction. Define on-call ownership and escalation routes during delivery planning rather than embedding unassigned people into this documentation.
